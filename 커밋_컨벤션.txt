1. 커밋 메시지 형식 — Conventional Commits
================================================================================

    <type>: <제목>
                        ← 빈 줄 한 줄
    <본문>


■ type 목록
--------------------------------------------------------------------------------

    feat        새로운 기능 추가
    fix         버그 수정
    docs        문서 작성/수정 (README, 가이드, 주석 등)
    style       동작에 영향 없는 변경 (들여쓰기, 줄바꿈, 세미콜론)
    refactor    기능 변화 없이 코드 구조만 개선
    test        테스트 코드 추가/수정
    chore       빌드, 설정, 패키지 등 잡무


■ 제목 규칙
--------------------------------------------------------------------------------
    - 명령형으로 작성          ("추가함" X  →  "추가" O)
    - 50자 이내
    - 끝에 마침표 없음
    - 무엇을 했는지 한눈에 들어오게


■ 본문 규칙
--------------------------------------------------------------------------------
    - 제목과 본문 사이에 반드시 빈 줄 한 줄
    - "무엇을" 보다 "왜" 중심으로 작성
      (무엇을 바꿨는지는 git diff가 이미 보여준다.
       왜 바꿨는지는 커밋 메시지에만 남는다)
    - 짧은 변경이면 본문 생략 가능


■ 예시
--------------------------------------------------------------------------------

    docs: 새 노트북 세팅 체크리스트 추가

    노트북을 옮길 때마다 clone/gh 설치/로그인 순서를 헷갈려서
    매번 다시 찾아보게 되어 절차를 문서로 고정함.

    ----

    fix: 0값 행이 DSD에 남는 문제 수정

    결산표에서 잔액 0인 계정이 삭제되지 않아 주석 합계가 어긋남.

    ----

    chore: .gitignore에 엑셀 임시파일 패턴 추가

2. 브랜치 규칙  ★ main에 직접 커밋하지 않는다 ★
================================================================================

main은 "언제 봐도 정상 동작하는 상태"로 유지한다.
모든 작업은 브랜치를 따로 파서 진행하고, 검토 후 main에 합친다.


■ 브랜치 이름 규칙
--------------------------------------------------------------------------------

    <type>/<간단한-설명>

    예시)
        docs/commit-convention
        feat/note-tangible-assets
        fix/zero-value-rows


■ 작업 흐름
--------------------------------------------------------------------------------

  1) 최신 main에서 새 브랜치 생성

        git switch main
        git pull
        git switch -c docs/commit-convention

  2) 파일 수정 후 커밋

        git add -A
        git commit -m "docs: 커밋 컨벤션 문서 추가"

  3) 브랜치를 원격에 푸시

        git push -u origin docs/commit-convention

  4) main에 합치기 — 둘 중 하나 선택

     [A] PR로 합치기 (기록이 남아 추천)

        gh pr create --fill
        gh pr merge --squash --delete-branch

     [B] 로컬에서 바로 합치기 (혼자 쓰는 저장소일 때)

        git switch main
        git merge docs/commit-convention
        git push
        git branch -d docs/commit-convention


================================================================================
3. 푸시 규칙
================================================================================

    "커밋해줘"       →  커밋까지만 하고 멈춘다
    "푸시해줘"       →  원격에 올린다

푸시는 원격에 반영되어 되돌리기가 번거로우므로 별도 지시를 받는다.
커밋 후에는 현재 브랜치가 origin보다 몇 커밋 앞서 있는지 보고한다.


================================================================================
4. 이 규칙을 Claude Code에 실제로 적용하는 법
================================================================================

★ 중요 ★
이 txt 파일은 사람이 읽는 문서일 뿐, Claude가 자동으로 읽지 않는다.
규칙이 실제로 적용되게 하려면 CLAUDE.md 파일에 넣어야 한다.

Claude Code는 작업 폴더 루트의 CLAUDE.md 를 세션 시작 시 자동으로 읽어들인다.
바꿔 말하면, 규칙을 아무리 잘 정리해 두어도 그 위치에 CLAUDE.md 가 없으면
Claude는 그 규칙의 존재 자체를 모른다.

  [적용 상태]  이 저장소에는 CLAUDE.md 가 이미 만들어져 있다.
               따라서 clone 만 하면 새 노트북에서도 규칙이 그대로 적용된다.
               규칙을 바꾸려면 이 txt가 아니라 CLAUDE.md 를 고쳐야 한다.
               (이 txt는 규칙의 배경과 예시를 담은 설명용 원본 문서)


■ 적용 범위에 따라 위치가 다르다
--------------------------------------------------------------------------------

  [프로젝트 단위]  <저장소 폴더>\CLAUDE.md
      - 그 저장소에서 작업할 때만 적용
      - git으로 함께 관리되므로 다른 노트북에서 clone 하면 규칙도 따라온다
      - 저장소마다 규칙이 다를 때 사용

  [전체 공통]      C:\Users\user\.claude\CLAUDE.md
      - 모든 프로젝트에 적용
      - 단, 이 파일은 그 PC에만 있으므로 노트북을 바꾸면 따라오지 않는다


■ 권장
--------------------------------------------------------------------------------
저장소 안의 CLAUDE.md 를 쓰는 것이 낫다.
clone만 하면 새 노트북에서도 규칙이 그대로 적용되기 때문이다.


■ CLAUDE.md 에 넣을 내용
--------------------------------------------------------------------------------

    ## 커밋 규칙
    - Conventional Commits 형식: `<type>: <제목>`
    - type: feat / fix / docs / style / refactor / test / chore
    - 제목은 명령형, 50자 이내, 마침표 없음
    - 본문은 제목과 빈 줄로 구분하고 "왜" 중심으로 작성
    - 커밋 전 git diff로 실제 변경분 확인

    ## 브랜치 규칙
    - main에 직접 커밋하지 않는다
    - 작업 시작 시 `<type>/<설명>` 형식으로 브랜치를 새로 판다
    - 작업 완료 후 PR 또는 merge로 main에 반영

    ## 푸시 규칙
    - "커밋해줘"는 커밋까지만. 푸시는 별도 지시를 받는다
